# Known Limitations

> Last verified 2026-07-07 against live testnet state (via CSPR.cloud) and current source, not just re-copied from a prior version of this doc.

## Smart Contracts

- **`grant_access` (defi-mock) is admin-gated in the deployed source** — verified in `contracts/defi-mock/src/main.rs`: the caller must equal `get_admin()` or the call reverts with `ERR_UNAUTHORIZED`. A previous version of this doc claimed there was no access control here; that was stale/incorrect.
- **Fixed 2026-07-07: `is_whitelisted` now takes a typed `AccountHash` (`CLType::ByteArray(32)`), not a free-form `String`.** Previously a caller passed an arbitrary string that was compared directly against the dictionary key (`AccountHash::to_string()` = lowercase hex, no prefix) - any client that didn't happen to format it identically got a silent "not whitelisted" instead of a clear error. All three entry points (`grant_access`, `revoke_access`, `is_whitelisted`) now take the same typed value, so this class of client-formatting bug can't happen. (Note: this changes the on-chain entry-point signature; nothing in `engine/`, `frontend/`, or `sdk/` calls `is_whitelisted` today, so no live caller is affected, but the deployed contract at the address in `README.md` still has the old signature until it's redeployed - source and testnet are in sync for every *other* entry point, just not this one yet.)
- **Redeploy attempted 2026-07-07, failed - deployed contract is still on the old signature.** With sign-off, tried installing the current `defi-mock` source (both as an in-place upgrade of the existing package name and as a genuinely new package name, to rule out the named-key-freeze gotcha) via `SessionBuilder().installOrUpgrade().buildFor1_5()` (the same pattern that worked for `stake-slashing` earlier the same day). Every attempt failed identically: `ApiError::InvalidArgument [3]`, ~9.44M gas consumed (payment/balance effects only, no contract-storage effects - rejected before `call()`'s own logic ran), `size_estimate` ~52KB (well under the `install_upgrade_lane`'s 750,000-byte chainspec limit, ruling out the wasm-size theory documented elsewhere in this file for a different bug). Isolated further by deploying the **unmodified, pre-hardening** `defi-mock` source under a fresh package name with the identical script - it failed with the exact same error, proving this isn't caused by the `is_whitelisted` signature change or any other source diff, and isn't the named-key-freeze issue either. Root cause not yet identified; likely an environment/node/SDK-version issue independent of contract content. No CSPR was lost beyond trivial gas on the failed attempts (~0.03 CSPR total across 4 tries). Next step if revisited: try `casper-client` (Rust CLI) instead of `casper-js-sdk` to rule out an SDK-side transaction-construction bug.
- **Fixed 2026-07-07: `defi-mock` now prevents duplicate whitelisting** — `grant_access` reverts with a new `ERR_ALREADY_WHITELISTED` (13) if the user already has an active (non-revoked) entry, instead of silently overwriting the previous proof_id/timestamp. Re-granting after a revocation still requires going through `revoke_access` first, so history stays explicit. Same redeploy caveat as above applies.
- **No input length validation on the engine/API side** — contract-side proof IDs are capped at 128 chars (`validate_proof_id` in `defi-mock`), but the Go API layer (`engine/internal/api/server.go`) does not itself cap request body/string sizes before forwarding.

## Engine

- **Fixed 2026-07-07: API key authentication.** Setting `API_KEY` now requires a matching `X-API-Key` header on every mutating request (anything other than `GET`/`HEAD`); read-only endpoints stay public. If `API_KEY` is unset (local dev/demo default), all requests are allowed through as before — this is a single shared secret, not per-agent keys/JWTs, which is an intentional simplification for a hackathon demo rather than a multi-tenant product. See `internal/api/server.go`'s `authMiddleware` and its tests.
- **Fixed 2026-07-07: KYC whitelist now survives a restart.** `kyc_whitelist` rows were being written (`SaveKYC`) since the schema was added, but nothing ever read them back — every restart silently lost every KYC grant even though Postgres had the data the whole time. `store.PG.LoadKYC()` + `kyc.DemoKYC.Restore()` now rehydrate the in-memory whitelist on server start when `DATABASE_URL` is set. Proofs and the model registry were already correctly persisted/reloaded; this closed the one remaining gap. The in-memory engine is still the live read path (for proofs) for latency reasons, not because Postgres isn't trusted — writes go to both, and everything is reloaded from Postgres on start.
- **Fixed 2026-07-07: `/aggregation/*` endpoints were pure stubs with no backing state** — `create-batch`/`add-proof`/`finalize` didn't store anything and `get-batch` unconditionally returned `proof_count: 0, status: "open"` for *any* `batch_id`, including ones that never existed. Now backed by a real (in-memory, process-local) batch registry: duplicate `batch_id` is rejected (409), unknown batches 404, adding past `max_proofs` or after finalization is rejected (409), and `get-batch` reflects actual proof count/status. This is still just bookkeeping, not real STARK aggregation math — `internal/aggregator` remains unwired dead code (separate, larger task). The batch registry itself is in-memory only and does not yet survive a restart (same class of gap proofs/KYC had before being fixed).
- **Hardcoded hash algorithm** — SHA-256 is the only supported hash. The config field `hash_algorithm` is present but not wired to alternative implementations.
- **Go engine cannot be cross-compiled to WASM** — The engine runs as a native binary only.
- **`/zk/verify-groth16` and `/zk/batch-verify` use a conceptual simulation, not real BN254 pairing math** — see `internal/zkverifier/groth16.go`'s own doc comment. It used to unconditionally return `valid: true` regardless of input; as of 2026-07-07 it actually runs the request through the simulator (still hash-based, still not real crypto, but no longer ignoring the input).
- **`/zk/groth16-real/prove` and `/zk/groth16-real/verify` (added 2026-07-07) are real Groth16** — actual R1CS circuit (`internal/zkverifier/gnarkzk`), actual trusted setup, actual BN254 pairing checks via `gnark`/`gnark-crypto`, verified to reject tampered proofs and tampered public inputs (see `gnarkzk`'s tests and a live HTTP round-trip). Scope: proves knowledge of a preimage `x` such that `MiMC(x) == hash`, not a full proof-of-inference circuit for an arbitrary model — that's a materially larger undertaking (Phase 3 "Layerwise ZK" in ROADMAP.md). The trusted setup is regenerated in-process on every server start (`gnarkzk.NewSetup()`), which is fine for demonstrating real cryptography but is explicitly NOT a production-grade multi-party ceremony.
- **Fixed 2026-07-07: post-quantum signing is real crypto, not a simulation, and is wired into `/pq/*`.** `internal/crypto` previously derived its "signature" by hashing part of the *private* key on sign but part of the *public* key on verify; since the public key was `SHA-256(private key)` (not a prefix of it), `Verify(pub, msg, Sign(priv, msg))` never actually returned true for two independently generated keys - every sign+verify code path was untested and non-functional. Replaced with: real Ed25519 (Go stdlib) for the classic component, real ML-DSA-65/FIPS 204 (`github.com/cloudflare/circl`) for the PQ component, and a genuine Lamport one-time hash-based signature standing in for the "SPHINCS+" slot (circl v1.6.1 has no Go SLH-DSA/SPHINCS+ implementation to depend on; Lamport is real, working, self-consistent crypto and the classic OTS ancestor of SPHINCS+'s WOTS+, but is single-use per key pair - reusing a key to sign a second message leaks private key material). The `/pq/sign-sphincs`, `/pq/verify-sphincs`, `/pq/hybrid-sign`, `/pq/hybrid-verify` endpoints now call this real code instead of unconditionally returning `valid: true`; verified via unit tests and a live HTTP round trip (genuine signature verifies, tampered message/signature is rejected).
- **STARK aggregation (`internal/aggregator`) remains a conceptual (hash-based) simulation** - real STARK proof composition is a materially larger undertaking (no mature Go library for arbitrary-circuit STARK recursion) - but it is now actually wired into `/aggregation/finalize` and a new `/aggregation/verify-batch/{id}` endpoint, exercising the package's real `CreateSTARKPack`/`UnpackAndVerify` code path instead of being unwired dead code.
- **Model registry (`internal/model`, `internal/inference.RegisterModel`) works end-to-end against a real Postgres and the on-chain `model-registry` contract's `register_model` entry point.** This note previously (incorrectly, and left stale for a while) claimed nothing called it — that was fixed earlier the same day the note was written: `POST /inference/register-model` (`inferenceRegisterModel` in `server.go`) calls it directly, and the frontend calls that endpoint from both `Models.tsx` and `AgentDemo.tsx` (`frontend/src/lib/api.ts`'s `registerModel`). Verified reachable end-to-end from the deployed product; this line was just never corrected until 2026-07-07 (second pass).

## SDK

- **Fixed 2026-07-07: the Go SDK (`sdk/client.go`) was entirely fictional — it targeted an imagined API surface that never matched the real server.** Paths like `/proofs/%s/verify`, `/models`, `/proofs/stark/aggregate`, `/proofs/groth16/%s/verify`, `/crypto/sphincs/sign` etc. don't exist in `engine/internal/api/server.go`; every method would have failed with 404 against the real, deployed API. `docs/SDK.md`'s example code (`sdk.NewClient(...)`, `.Submit()`, `.Verify()`, `.List()`) also didn't match the actual (previous) client's method names (`NewCasperProverClient`, `SubmitProof`, etc.) — the doc was never kept in sync with the code, let alone the code with the real API. Rewrote `sdk/client.go` from scratch so every method maps 1:1 to a real registered route (verified against `server.go`'s `mux.HandleFunc` list), added `sdk/client_test.go` (HTTP round-trip tests against a fake server, including the auth-token path), and fixed `docs/SDK.md`'s example to match.
- **Fixed 2026-07-07: `sdk/` had no `go.mod`, so it wasn't a real importable/publishable Go module** (import path in `docs/SDK.md` didn't resolve to anything) and wasn't covered by CI at all. Added `sdk/go.mod` (separate module, own CI jobs `sdk-test`/`sdk-lint` in `.github/workflows/check.yml`) so it can be `go get`'d independently of `engine/` and is now actually build/vet/test/lint-checked on every push.
- **Fixed 2026-07-07: `docs/SDK.md` instructed `go run sdk/mcp_server.go`, which was never possible** — that file is `package sdk` with no `func main`, so `go run` on it fails immediately. Added a real entry point at `sdk/cmd/mcpserver` that wires ~12 of the 22 tools in the MCP manifest to real API calls via the new client; the other ~10 (`list_models`, `get_task_status`, `submit_batch_task`, etc.) have no backing API endpoint at all (aspirational manifest entries left over from `internal/model`/`internal/worker`, which are themselves unwired dead code) and now return a clear "not implemented" JSON-RPC error instead of the loop hanging or silently no-op'ing.

## Frontend

- **Fixed 2026-07-07: `/lab/agent-demo`'s Step 2 (and effectively every step after Step 1) always failed with "... not available. Complete Step N first."** even right after the previous step visibly succeeded. Root cause: `AgentDemo.tsx`'s per-step `action` closures were created once (in `initialSteps`, only re-applied by `resetDemo`) and captured `modelId`/`proofId`/`batchId` from whatever render was active *when the step's closure was created* — calling `setModelId` after Step 1 triggered a re-render, but the already-in-flight `runFullDemo` loop kept using the stale closures from before that render, so Step 2 always read `modelId` as its initial empty string. Fixed by routing the actual read/write of these three values through `useRef`s that every step closure reads via `.current`, so they always see the latest value regardless of when the closure was created. Verified with `npm run build` (clean) and manual trace of the step 1→2→...→6 data flow.
- **Verified 2026-07-06 audit findings not reproduced in current source** (re-checked 2026-07-07): the `/lab/pqcrypt` → 404 report doesn't reproduce — `App.tsx`'s route is `/lab/pq-crypto` and matches `PQCrypto.tsx`'s nav link; likely already fixed since the audit or was itself a stale finding. The "Demo/Real toggle not implemented" report is accurate but is a planned feature (see `ROADMAP.md` Phase 2), not a regression - nothing in source implements a toggle today. The "`/lab` button not flush to edge" and "back button → black screen" reports were **not verified either way** — no in-app "back" navigation exists in source (likely refers to the browser's native back button, which needs a live click-through to diagnose, not just code review) and the layout issue needs a visual check; flagging as unverified rather than guessing at a CSS fix blind.
